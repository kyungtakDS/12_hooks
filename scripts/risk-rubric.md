# Risk Score 루브릭

변경의 위험도를 0~100 점으로 환산한다. 항목별 점수를 매기면 총점은 도구가 더한다.

## 평가 항목

| 키 | 항목 | 만점 | 무엇을 보는가 |
|---|---|---:|---|
| `security` | 보안 | 30 | API 키·시크릿 노출, 명령 주입, SQL 주입, 경로 조작, 권한·인증 우회, 안전하지 않은 역직렬화 |
| `scope` | 변경 범위 및 복잡도 | 20 | 과도한 변경, 한 커밋에 섞인 여러 책임, 복잡도 증가, 검토하기 어려운 대규모 변경 |
| `breaking` | Breaking change | 20 | 기존 API·함수 시그니처·설정 키·파일 구조·CLI 사용법의 비호환 변경 |
| `tests` | 테스트 및 검증 | 15 | 테스트 누락, 깨질 가능성이 있는 테스트, 경계조건 미검증, 빈 테스트나 skip 으로 우회 |
| `ops` | 마이그레이션 및 운영 영향 | 15 | 배포·데이터·설정·의존성 변경, 롤백 불가, 마이그레이션 누락 |

## 점수를 매기는 원칙

1. **근거가 없으면 0점이다.** diff 에서 짚을 수 있는 구체적 사실이 없으면 그 항목은 0 이다.
   "혹시 모르니" 로 점수를 주지 않는다.
2. **이 변경이 새로 도입한 것만 센다.** 기존 코드에 원래 있던 문제는 점수에 넣지 않는다.
3. **스타일·네이밍·취향은 점수를 올리지 않는다.**
4. 항목별 점수는 만점을 넘을 수 없다.
5. 각 항목의 근거(`evidence`)는 한 줄로 쓴다. 문제가 없으면 `"문제 없음"` 이라고 쓴다.

### 항목별 점수 감각

- **0** — 해당 위험이 전혀 없다.
- **만점의 1/3 이하** — 사소하다. 고치면 좋지만 막을 일은 아니다.
- **만점의 2/3 내외** — 실제로 문제가 될 수 있다. 조건을 명시할 수 있다.
- **만점** — 즉시 피해가 발생한다. (예: 보안 30점 = 실제 시크릿이 커밋에 포함됨)

## 위험 등급

총점으로 등급을 정한다. 등급 계산은 도구가 하므로 모델이 직접 쓰지 않는다.

| 총점 | 등급 |
|---|---|
| 0–20 | Low |
| 21–40 | Moderate |
| 41–60 | High |
| 61–80 | Very High |
| 81–100 | Critical |

## 출력 형식

**JSON 객체 하나만** 출력한다. 앞뒤에 설명을 붙이지 않는다.

```json
{
  "categories": {
    "security":  {"score": 0, "evidence": "문제 없음"},
    "scope":     {"score": 2, "evidence": "README 와 workflow 일부 변경"},
    "breaking":  {"score": 0, "evidence": "없음"},
    "tests":     {"score": 5, "evidence": "신규 동작 테스트 일부 부족"},
    "ops":       {"score": 0, "evidence": "없음"}
  },
  "findings": ["파일:줄 — 발견된 문제"],
  "recommendations": ["권장 수정 사항"],
  "positives": ["잘된 점"],
  "verdict": "merge 가능"
}
```

`verdict` 는 `"merge 가능"`, `"수정 후 merge"`, `"merge 차단"` 중 하나다.

`findings` · `recommendations` · `positives` 는 없으면 빈 배열로 둔다.
억지로 채우지 않는다.
